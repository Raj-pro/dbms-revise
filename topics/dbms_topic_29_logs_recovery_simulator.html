Database Logs and Recovery

Learn how a DBMS uses log records, checkpoints, undo, and redo after failures.

1. Why do databases need recovery?

A system can crash while a transaction is running or shortly after it commits. Recovery uses persistent information to restore the database to a correct state.

UNDO

Reverse changes from transactions that did not commit, where required by the recovery scheme.

REDO

Reapply changes from committed transactions whose updates may not yet have reached the data files.

Checkpoint

A recovery marker that can reduce how much log history must be examined; it does not mean the log can always be discarded.

2. Explore log records

Example transaction T1 transfers ₹500 from A to B. A simplified log may record old and new values.

Log recordMeaning
<START T1>Transaction T1 begins.
<T1, A, 2000, 1500>T1 changes A from 2000 to 1500.
<T1, B, 1000, 1500>T1 changes B from 1000 to 1500.
<COMMIT T1>T1 successfully commits.

This teaching format stores old and new values. Actual log formats vary. With write-ahead logging (WAL), the relevant log record must be made persistent before the corresponding data page is written.

4. UNDO and REDO at a glance

SituationTypical recovery actionReason

Transaction committed but some data pages were not writtenREDO, if requiredEnsure committed changes appear in the recovered database.

Exam recap

  • Log records track transaction actions and help recovery.
  • UNDO: reverse changes that should not remain.
  • REDO: reapply changes that should remain.
  • WAL: required log information is persisted before the associated data page is written.
  • Checkpoint: reduces recovery work, but does not automatically remove the need to examine other log records.
