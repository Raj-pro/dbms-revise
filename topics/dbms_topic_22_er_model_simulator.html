ER Model (Entity–Relationship Model)

Learn entities, attributes, relationships, cardinality, participation, weak entities, and mapping ER diagrams into tables.

1. What is an ER model?

An ER model is a plan or blueprint of a database. It shows what things we store and how those things are connected, before we create actual tables.

Entity

A real-world object or concept we want to store.

Examples: Student, Course, Employee

Attribute

A property that describes an entity.

Student: ID, Name, Age

Relationship

An association between entities.

Student enrolls in Course

Classic Chen notation: rectangles represent entities, diamonds represent relationships, and ovals (not shown here) represent attributes.

3. Cardinality ratio — interact with the example

Cardinality tells us the maximum number of entities that can be associated through a relationship.

Many students can take many courses: M:N (many-to-many).
RatioMeaningExample
1:1One on each sidePerson — Passport (simplified rule)
1:NOne A can relate to many B; each B relates to at most one ADepartment — Employees
N:1Many A relate to one BMany employees — one department
M:NMany on both sidesStudents — Courses

4. Participation constraints

Participation tells us whether involvement in a relationship is mandatory or optional.

Total participation

Every entity in that entity set must participate in the relationship.

Example: Every dependent must be associated with an employee.

Double line in classic ER notation

Partial participation

Some entities may not participate.

Example: An employee may not manage any project.

Single line in classic ER notation

Remember: cardinality = “how many?”; participation = “must it happen?” They are different constraints.

5. Weak entities and identifying relationships

A weak entity cannot be uniquely identified using its own attributes alone. It depends on an owner (strong) entity and typically uses a partial key together with the owner's key.

EMPLOYEE
(EmployeeID)
HAS
DEPENDENT
(Name)

For example, a dependent's name may be unique only within one employee's family. The key can be (EmployeeID, DependentName). The identifying relationship and weak entity are drawn with double diamonds and double rectangles in classic notation.

6. Map an ER model to relational tables

Try selecting a relationship type and see a common mapping rule.

Example schema: students enroll in courses (M:N)

STUDENT(StudentID PRIMARY KEY, Name) COURSE(CourseID PRIMARY KEY, Title) ENROLLMENT( StudentID REFERENCES STUDENT(StudentID), CourseID REFERENCES COURSE(CourseID), EnrolledOn, PRIMARY KEY (StudentID, CourseID) )

The relationship table stores the two foreign keys; together they form a composite primary key when a student can enroll in a course only once.

Topic recap

  • Entity = thing; attribute = property; relationship = association.
  • Cardinality describes maximum relationship counts (1:1, 1:N, M:N).
  • Participation is total (mandatory) or partial (optional).
  • A weak entity relies on an owner entity for identification.
  • When mapping M:N, create a separate relationship table with foreign keys.
