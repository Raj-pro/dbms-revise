Recoverability of Schedules

Learn when a transaction can safely commit in relation to the transactions whose data it reads.

1. Why does recoverability matter?

Suppose T2 reads a value written by T1. If T2 commits before T1, and T1 later aborts, T2 has committed using a value that should never have become permanent. This can make recovery unsafe.

Recoverable schedule

If T2 reads from T1, T2 commits only after T1 commits.

Non-recoverable schedule

T2 commits before T1, even though T2 read a value written by T1.

Cascading rollback

If T1 aborts, transactions that read its uncommitted value may also need to abort.

3. Three important schedule classes

ClassRule of thumbBenefit
RecoverableIf Tj reads from Ti, then Ti must commit before Tj commits.Prevents a dependent transaction from committing before its data source commits.
CascadelessA transaction reads only values written by committed transactions.Prevents cascading aborts caused by dirty reads.
StrictNo transaction may read or write an item written by an uncommitted transaction.Simplifies recovery and prevents dirty reads and dirty writes.
Relationship: Strict ⟹ Cascadeless ⟹ Recoverable. The reverse implications do not always hold.

4. Remember with a simple example

Schedule: W1(X), R2(X), C1, C2

  1. T1 writes X.
  2. T2 reads the value written by T1.
  3. T1 commits first.
  4. T2 commits after T1.

This is recoverable because the transaction that produced the value commits before the transaction that read it.

Exam recap

  • Recoverability is about commit ordering after read-from dependencies.
  • Recoverable does not necessarily mean cascadeless.
  • Cascadeless schedules avoid dirty reads.
  • Strict schedules also prevent dirty writes.
