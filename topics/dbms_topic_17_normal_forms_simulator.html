Database Normal Forms

Learn why tables are normalized, how each normal form works, and how to recognize common violations.

1. Why normalize?

Normalization organizes database tables to reduce duplicate data and prevent insertion, deletion, and update anomalies. Each higher normal form adds stronger conditions.

1NF → 2NF → 3NF → BCNF → 4NF → 5NF → 6NF

This is a learning roadmap, not a claim that every database must always be decomposed all the way to 6NF.

1NF — First Normal Form

Each cell contains one atomic value, with no lists or repeating groups in a single cell.

Not 1NF: StudentID S1, PhoneNumbers = “111, 222”.
1NF-friendly: store each phone number as a separate row, or use a related phone table.

2NF — Second Normal Form

Must be in 1NF, and every non-prime attribute must depend on the whole candidate key—not just part of a composite candidate key.

Key: (StudentID, CourseID). If StudentID → StudentName, StudentName depends on only part of the key: a partial dependency.

3NF — Third Normal Form

Must be in 2NF. For every non-trivial FD X → A, either X is a superkey or A is a prime attribute (part of some candidate key).

Common beginner pattern: remove transitive dependency of non-key attributes on a key.

BCNF — Boyce–Codd Normal Form

For every non-trivial FD X → Y, X must be a superkey.

BCNF is stricter than 3NF: it does not provide the prime-attribute exception.

4NF — Fourth Normal Form

Must be in BCNF, and every non-trivial multivalued dependency X ↠ Y must have X as a superkey.

Example pattern: a person has multiple independent skills and multiple independent languages; storing every combination creates repetition.

5NF — Fifth Normal Form

Also called Project-Join Normal Form. Non-trivial join dependencies must be implied by candidate keys; decomposition should not require avoidable multiway join redundancy.

Usually appears in advanced cases where a relation can be reconstructed from three or more projections.

6NF — Sixth Normal Form

A relation has no non-trivial join dependencies (other than those implied by keys); in practice, 6NF often uses irreducible relations, especially for temporal databases.

It is advanced and not usually required for everyday transactional schemas.

Key terms for normal forms

Prime attribute: belongs to at least one candidate key.

Non-prime attribute: belongs to no candidate key.

Partial dependency: a non-key attribute depends on a proper subset of a composite candidate key.

Transitive dependency: a key determines a non-key attribute through another attribute or set of attributes.
